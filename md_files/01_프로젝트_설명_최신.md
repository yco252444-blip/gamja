## 1. 한 줄 소개

XIAO ESP32S3 센서 노드가 온도·습도·가스 데이터를 MQTT로 보내고, 라즈베리파이가 이를 중계·저장하면서 **RandomForest 회귀 모델로 120초 뒤 심부온도를 예측**해 미생물 처리기의 히터 제어 판정(정상/저전력 모드)을 내리고, ESP32가 안전 조건을 다시 검증한 뒤 릴레이를 구동하는 구조를 목표로 한 프로젝트. 사용자 앱(microbe-app)은 상태를 미생물 캐릭터의 건강도로 시각화한다.

## 2. 문제 정의 — 기존 방식의 한계

가정용 스마트 플러그/온습도계 대부분은 "지금 값이 기준선을 넘었는가"만 보는 임계값 방식이다.
- 기준을 넘은 **뒤**에야 반응한다(이미 과열·낭비 시작).
- 순간값만 봐서 서서히 오르는 추세와 튀는 노이즈를 구분하지 못한다.
- 여러 센서(온도·습도·가스·전력) 간 관계를 종합하지 못한다.

## 3. 핵심 아이디어 — 예측형 제어

- 입력: 최근 60초(1Hz)의 센서 시계열에서 뽑은 특징(현재값·표준편차·기울기).
- 출력: **120초 뒤 심부온도**(회귀).
- 활용: 예측이 목표온도에 도달할 것 같으면 히터를 **미리 끄는** "저전력 모드"(예측 조기 OFF), 투입물로 인한 급변(뜨거운/찬 물체 투입) 감지.
- **현재 상태(중요)**: 모델·판정 코드·단위 테스트는 있으나 §9.4의 한계로 "AI가 절전에 기여한다"는 주장은 **아직 실측으로 뒷받침되지 않음**.

## 4. 시스템 구조 개요

```
[A. 실제 하드웨어 경로]
XIAO ESP32S3 --MQTT sensors(1Hz)--> Raspberry Pi
                                      ├─ mosquitto 브로커
                                      ├─ gateway(Node.js, Express+Socket.IO): 대시보드·REST API·inference 토픽 수신 표시
                                      ├─ training-data-logger: hardware 프레임만 CSV 저장
                                      └─ predict_service.py (수동 실행): 60프레임 윈도우 → RF 예측 → 히터 판정
                                           └─ smarthome/<id>/inference (heater_command 등) ──> ESP32
ESP32: heater_command 수신 → 자체 안전 재검증(과열·연속가열·명령 stale·MQTT 재연결·센서 무효) → 릴레이

[B. 앱 경로, 부분구현]
microbe-app (Expo/React Native, 소스 ZIP 미포함) --HTTP--> microbe-server (FastAPI, 하드코딩 mock)
```

- **A와 B는 여전히 연결되지 않음**. `microbe-server/server.py`는 온도 24.5, 습도 52.0, CO2 730, NH3 1.2, 목표온도 24.0 등 **고정 상수**를 반환한다(직접 확인).
- `predict_service.py`는 Pi 배포 자동화(`bootstrap.sh`, systemd 유닛 2개: gateway·data-logger)에 **포함되어 있지 않음**(직접 확인: 배포 스크립트에 predict 언급 없음) → 수동 실행.

## 6. 전력 측정 — INA219

- 목적: 실제 소비전력 실측 → 절감 효과 검증 기준값.
- **문서 간 모순**(ZIP 내 3개 인수인계 문서):
  - `센서_하드웨어_인수인계`: 보드 교체 후 D4/D5에서 I2C 0x40 ACK 정상(주소 응답만 확인, 전압·전류 실측은 안 함).
  - `펌웨어_INA219_릴레이_통합_인수인계`: 다른 보드에서 D4/D5, D6/D7 모두 무응답, 통합 코드는 작성했으나 값은 null.
  - 최신 `SensorConfig.h`: `ENABLE_INA219=false`.
- **결론**: 소비전력 실측 데이터는 **0건**. "절전형"의 정량 근거가 없음.

## 7. 통신 구조 — ESP32 → MQTT → 게이트웨이

### 7.1 기본 흐름 **[구현 완료]**
- `smarthome/<device_id>/sensors` 1Hz JSON: `device_id`, `sequence`, `data_source`(hardware/mock), `sensors`, `valid`, `actuators`.
- 신규: `smarthome/<id>/inference` 토픽(예측 온도·제어 권고·`heater_command`·`control_mode`·`model_version`)을 게이트웨이가 수신·표시(직접 확인: `server.js`가 inference 필드를 파싱).

### 7.2 MQTT 헬스체크 / 좀비 연결 복구 **[구현 완료 — 센서 노드 측]**
- 5초 간격 nonce publish/echo로 RTT 확인, 15초 무응답 시 stale 판정 → 강제 재연결. keepAlive 10초, 소켓 타임아웃 2초.
- 게이트웨이의 30초 오프라인 감지는 별개 로직. 게이트웨이 쪽 healthcheck RTT 처리 코드는 이 문서 작성 시 재확인하지 않음([미확인]).
- 실측 로그(07-31 문서 기재): 7분 캡처, 순단 1회 후 68ms 재연결, 재부팅·Guru Meditation 0건.

## 8. 게이트웨이 서버 (Raspberry Pi) **[구현 완료]**
- Node.js(Express+Socket.IO). REST: `GET /api/devices`, `/api/devices/:id`. Socket.IO: `devices:init`, `device:update`, `led:set`.
- 상태는 인메모리(재시작 시 소실). 학습 CSV는 `training-data-logger.js`가 hardware 프레임만 저장.
- 배포: `bootstrap.sh`(mosquitto·Node·systemd 유닛), `smarthome-gateway.service`, `smarthome-data-logger.service`(`Restart=on-failure`).

## 9. AI 추론·제어 구조

### 9.1 학습 (`ai-training/build_dataset_and_train.py`) — 직접 확인
- 입력 특징 13개: {심부온도·공기온도·습도·MQ-137} × {현재값, 60초 표준편차, 60초 기울기} + (심부−공기 온도차).
- 타깃: **120초 뒤 심부온도**. 60초 윈도우, 2초 stride.
- 모델: 초기 Ridge는 검증 MAE 약 15억 ℃로 폭주해 폐기(`extrapolation blowup`), **RandomForest 채택**. 트리를 C 배열(`CoreTempModel.h`)과 JSON(`core_temp_model.json`)으로 내보냄.
- `model_version = mvp-temp-regression-1.0`.

### 9.3 제어 판정 (`predict_service.py`) — 직접 확인
- 상수: 목표 **37.0℃**, 정상모드 ON 1.0℃ 아래·OFF 목표 도달, 저전력 모드 예측 조기 OFF 마진 0.2℃, 안전한계 42℃, 센서 stale 15초.
- 모드: `normal`(히스테리시스) / `low_power`(예측이 목표−0.2℃에 닿으면 조기 OFF, 예측 미준비 시 normal로 폴백).
- 급변 감지: 10초 창에서 ±2℃ 변화가 2회 확인되면 뜨거운/찬 투입으로 판정(쿨다운 20초). **dry-run 전용**, 릴레이에 적용 안 함.
- 안전 우선순위: 센서 무효/NaN·stale·과열이 항상 최우선.
- ESP32 측 재검증 상수: `MAX_SAFE_TEMPERATURE_C=42`, `MAX_CONTINUOUS_HEATING_SEC=300`, `MIN_RELAY_HOLD_SEC=10`, `COMMAND_STALE_SEC=20`. Pi 값과 수동 동기화 필요(코드 주석).
- 단위 테스트 3종(`test_heater_control.py`, `test_predict_service.py`, `test_rapid_change.py`): 예측값을 손으로 넣은 로직 테스트이며 **실제 하드웨어·모델 성능 검증이 아님**.

### 9.4 검증된 한계 (이 문서에서 가장 중요한 부분) — 2026-09-21 검증
1. **학습 분포와 제어 목표 불일치**: 학습은 실온(약 25℃), 제어 목표는 37℃. 히터 ON 데이터·음식물·미생물 투입 데이터가 0.
2. **예측 상한 31℃ 클립**: `pred_clip_high = 31.0`(학습 최대+2℃)이 `predict_service.py:181`에서 적용되어 **예측이 목표 37℃ −0.2℃에 도달할 수 없음** → 저전력 모드의 "예측 조기 OFF" 분기가 구조적으로 발동 불가.
3. **검증 수치의 의미(2026-09-21 재실행 검증)**: 검증 MAE 0.032℃는 재현되지만, 245개 샘플이 연속 구간 2개에서만 나왔고 검증 49개는 한 구간·정답 전부 25.5℃(표준편차 0)였다. "2분 뒤 = 지금 값" 기준선 MAE가 검증셋에서 0.000으로 **RF보다 좋다.** 구간 교차검증에서도 RF 0.30~0.44℃ vs 기준선 0.00~0.18℃로 **기준선이 항상 우세**. DS18B20이 9-bit라 0.5℃ 단위 출력(정답이 25.5·26.0 두 값뿐). **현 모델은 지금값 유지보다 나은 예측력이 없다.**
4. **레거시 권고 경로**: `control_recommendation`의 기준은 학습 데이터 중앙값(25.5℃)이라 실제 처리기와 무관한 데모 임계값.
5. **"온디바이스"와 구조 불일치**: 추론이 Pi에서 실행된다(ESP32 아님). 정확한 표현은 "엣지(Pi) 추론".
6. 최신 스냅샷 설정(MQ-137·릴레이 비활성)에서는 추론·제어 체인이 실제로 돌지 않을 가능성이 있음(§5 주의).

## 11. 시연 흐름 (현재 실제로 보여줄 수 있는 것)

1. ESP32 전원 → Wi-Fi → MQTT 1초 발행. 게이트웨이 대시보드 실시간 갱신·온라인/오프라인.
2. MQTT 단절 시 헬스체크 로그(nonce RTT, stale 감지, 재연결).
3. Pi에서 `predict_service.py`를 **수동 실행**하면 inference 토픽으로 예측·`heater_command`(dry-run) 확인 가능 — 단 §9.4 한계 명시 필수.
4. 앱은 별도 트랙(mock). 두 트랙 미연결.

## 12. 기대 효과
- **정량적 절감률은 실측되지 않았다.** 앱의 "이달 절감 14,200Wh"는 상수. 실측 전력 데이터 0건.
- 정성적: 추세를 읽어 과열·낭비를 사전 예방하는 구조, 비전문가용 캐릭터 UI.

## 13. 향후 계획 (우선순위 재정렬)
1. **실운전 데이터 수집**: 실제 목표 온도 대역(약 37℃)에서 히터 ON/OFF·뜨거운/찬 투입 데이터 6시간+, **다른 날 검증셋 분리**.
2. **기준선 비교**: 지금값 유지 / 히스테리시스만 / RF — 오버슈트와 소비전력 기준.
3. `pred_clip_high` 제거·재학습 후 예측이 목표 온도에 닿는지 확인.
4. **소비전력 실측**: INA219 정리 또는 USB/스마트플러그형 전력계로 대체, Wh 기록.
5. 릴레이 ON 극성 검증, 챔버(단열 용기+발열체+교반) 제작(`3d-model/` 폴더는 비어 있음).
6. MQ-137/138 재활성화·ppm 환산 또는 추세 경고로 한정, DHT11 유효율 개선.
7. `predict_service`를 systemd 유닛으로 배포에 편입, 게이트웨이 healthcheck 처리.
8. 앱 소스를 저장소에 포함하고 mock 서버를 게이트웨이 데이터로 교체, 성과·마이·알림 화면 서버 연동.
9. 민감정보 정리(`.env`의 Edge Impulse API 키 재발급, `secrets.h`).
