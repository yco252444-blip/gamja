# Oink AI 회의록 (2026-09-21)

4개 담당(펌웨어·제어 / 하드웨어·안전 / 데이터·AI / 통신·대회)이 각자 조사한 뒤 종합했다. 담당 의견은 코드·문서 조사 결과이고 대부분 원본을 직접 재확인하지 않았다(**미검증**). 데이터·AI 담당만 분석 스크립트를 돌려 MK1 수치를 재현했다고 보고했다. 시크릿 값은 이 문서에 쓰지 않는다.

| 항목 | 내용 |

## 1. 4명이 합의한 것
- 히터 결정은 ESP32 안에서만 한다. 서버·MQTT·클라우드는 로그와 시각화 전용이다.
- 소프트웨어 안전은 2차 방어이고, 1차는 하드웨어 차단(퓨즈 + KSD301 + 열퓨즈)이다.
- 계획서 §3 구성은 확정이 아니라 가정이다. 부품 정보 없이 도식 그대로 확정하지 않는다.
- 개발 순서는 dry-run → 더미 부하 → LIVE.

## 2. 담당별 핵심

**펌웨어·제어**
- MK1 위험: WiFi 재연결 무한 대기 중 안전 게이트 정지(`.ino:783-786`), 연속 가열 300초 상한이 쿨다운 없어 무력(`.ino:181-216`), DS18B20 85.0 미필터, 워치독 0건, 릴레이 로직은 현재 false라 검증된 적 없음.
- 안전 로직은 순수 C++로 분리해 PC에서 테스트한다. 폐기: `heater_command` 경로, `CoreTempRegressionEngine`, 슬라이딩 윈도우.

**하드웨어·안전**
- INA219 도식(00:84)은 로우사이드 션트라 ON일 때 버스 전압이 약 0V. 전력은 `12V 실측값 × I`로 계산하거나 하이사이드로 옮긴다. (펌웨어 담당도 같은 지적)
- 04번 문서의 10k/20k 분압은 ADC 유효 범위(2.9V)를 넘는다. 03번의 10k/12k(약 2.7V)를 쓴다.
- 퓨즈 3~5A는 INA219 션트 한도(0.1Ω 기준 3.2A)보다 크다.
- MOSFET 단락 고착은 SW·퓨즈로 못 막는다. 서모스탯·열퓨즈의 장착 위치와 오프셋 검증이 필요하다.
- 서모스탯 설정 온도를 챔버 42℃에 그대로 맞추면 패드 표면 온도 때문에 오차단될 수 있다.
- DS18B20이 D2/GPIO3인데 GPIO3이 스트래핑 핀일 수 있다 (데이터시트 미확인).

**데이터·AI**
- MK1 기준선 결과는 재현됨: RF가 "지금값 유지"를 못 이김. 다만 이 데이터로는 "이길 수 없다"도 증명되지 않음.
- 실제 이어진 데이터는 약 39분(1,946행). 문서의 "7시간"은 시계상 길이. 심부온도 범위는 23.5~29.0℃.
- 제안(수치는 가정): 규칙 제어 기본 + AI는 shadow 로깅, 홀드아웃과 E3 조건 충족 시에만 승격, 10/31 판정.
- 로깅은 서버 수신시각 대신 기기 시각 + 로컬 버퍼링 + seq. A/A 실험으로 잡음 바닥을 먼저 측정.

**통신·대회**
- 대시보드는 현재 MK1 데이터를 표시하지 못함 (토픽 필터 `xiao/…`만 통과, `status` 형식 불일치). 실행 검증은 안 함.
- 인증 없는 제어 API(`/led`, `/detect`, `/framerate`)와 카메라 코드는 처리기에 불필요. 삭제 후보.
- 익명 MQTT + 0.0.0.0 바인딩(F6). `heater_command`가 MQTT로 흐르는 구조가 남으면 로컬 제어가 주장에 그침.

## 3. 원격 확인·분석 요구 반영 (통신 담당 의견 정정)

통신 담당은 "Railway 불필요, 로컬 브로커 + 로컬 저장"을 제안했으나, 사용자가 원격 확인과 클라우드 분석이 필요하다고 했으므로 이 부분은 **정정**한다. 삭제 후보에서 `remoteMirror`와 Supabase 연동은 제외한다.

| 안 | 경로 | 비고 |
|---|---|---|
| A | ESP32 → MQTT(Railway 브로커) → 서버 → Supabase/Firebase | 기존 대시보드·`RAILWAY_SETUP.md` 재사용. TCP 프록시 필요. |
| B | ESP32 → HTTPS → Supabase/Firebase 직접 | 브로커 불필요. 기기에 쓰기 자격증명이 들어가므로 노출 위험 관리 필요. |
| C | ESP32 → 로컬 MQTT(노트북, 전용 공유기) → 로컬 백엔드 → Supabase upsert(나가는 요청만) → Vercel 뷰어 | 과거 프로젝트(§3-1)에서 실제 구현·실측한 구조. Railway 불필요. 노트북과 그 노트북의 인터넷이 있어야 함. |
| Vercel | 프론트/REST 용도로 가능 (사진 데이터 없을 때) | 상시 TCP 브로커는 못 띄움. 브로커가 필요하면 Railway. |

### 3-1. 과거 프로젝트 참고 (`202607_ai_smarthome_mento\AI_makerton`)
읽기 전용으로 구조와 문서만 확인했다. `.env`, `.env.local`, `.mcp.json`, `supabase\.temp`는 열지 않았다. 아래는 그 프로젝트 문서(PROGRESS.md, README.md 등)의 기록이며 이번에 재실행해 검증한 것은 없다(**미검증**).

- `AI_makerton_base`(로컬 대시보드 + Aedes 브로커 + Supabase 연동), `_deploy_railway`(Railway 배포), `_deploy_vercel`(원격 뷰어), `_deploy_ap`, `_deploy_cm11106`, `help`(인수인계·릴레이 진단 문서).
- **Supabase 구조**: `device_state`(기기별 최신 상태 1행 upsert)와 `telemetry_events`/`detection_events`(이력, `payload jsonb`). RLS는 anon에 SELECT만 허용하고, 쓰기는 로컬 백엔드의 서비스 롤 키만 한다. 즉 **서비스 키가 기기가 아니라 서버에만 있다.** 이 패턴은 §3의 "기기에 서비스 키를 넣지 않는다" 조건과 맞는다.
- **Vercel 뷰어**: `device_state`를 Realtime으로 구독. anon key는 읽기 전용이라 프론트에 노출돼도 된다는 설계. 카메라 영상은 Supabase로 못 보내서 제외했다. Oink는 카메라를 안 쓰면 이 제약이 없다.
- **Railway는 카메라 프레임을 노트북 없이 원격에서 보려고 나중에 추가한 것**이다 (MQTT 프레임 릴레이). 센서 텔레메트리만이면 안 C로 충분했을 가능성이 있다.
- **GitHub → Vercel 자동 배포**: 레포 루트에서 `vercel link`하면 GitHub 연동이 자동으로 됐고, 서브폴더에서 링크하면 `vercel git connect`가 실패했다는 기록이 있다.
- **분석용으로는 재검토 필요**(제안): 이력 테이블이 `payload jsonb` 통짜라서, Oink 분석(E1~E5)에는 `temp_c`, `heater_cmd`, `reasons`, `seq` 같은 컬럼을 분리하는 편이 낫다. `telemetry.h`의 JSON 필드와 맞추면 된다.
- **릴레이 진단 교훈**(`help/`): 릴레이 기판 LED를 트리거 판정 근거로 쓰지 않는다, 외부 5V의 −와 XIAO GND를 공통 접지한다, INA219 실패 시 팬(부하) ON 금지. 세 가지 모두 Oink 히터 시험에도 적용된다. 해당 진단 스케치(`fan_relay_test`)는 문서상 컴파일·업로드·실물 시험을 한 번도 거치지 않은 초안이다.

공통 조건 (안 선택과 무관하게 지킬 것):
- 원격·클라우드는 **텔레메트리 전용**이다. 서버·인터넷이 끊겨도 제어와 안전은 ESP32에서 동작해야 한다.
- 대회장 인터넷이 없거나 불안정할 수 있으므로 기기 로컬 버퍼링과 seq 재전송으로 누락을 막는다. 운영사에 인터넷 제공 여부를 문의한다.
- 분석용이므로 기기 벽시계 시각과 run 메타데이터(run_id, exp, arm)가 필요하다.
- 기기에 서비스 키를 넣지 않는다. 쓰기 전용 권한(RLS insert-only 등)으로 제한하는 방안을 검토한다 (미검증).
- 원격에서 히터를 조작하는 경로는 두지 않는다. setpoint 변경이 필요하면 인증과 범위 제한을 둔다.

## 4. 계획서·문서 정정 필요
1. D4 "85.0 필터 유지"는 틀림. MK1에 필터 없음, 신규 구현.
2. 00:84 INA219 배치 (로우사이드 문제).
3. 04번 10k/20k 분압 예시 폐기.
4. 퓨즈 3~5A와 션트 한도(3.2A) 불일치.
5. "7시간 수집"은 실제 이어진 데이터 약 39분. 심부온도 범위 23.5~29.0℃.
6. MK1 코드의 DS18B20 핀 주석은 GPIO27, 실제 코드는 GPIO3.
7. 인수인계 문서 간 모순: INA219 핀(D4/D5 vs D6/D7), COM6 vs COM8.
