## 0. 읽는 법

- **[직접]** = 원문 PDF/HTML을 내려받아 텍스트를 직접 추출해 확인한 값. 파일 열람 후 인용.
- **[2차]** = 검색결과 요약, 미러 사이트, 커뮤니티 글로만 확인. 원문 미열람.
- **[계산]** = 위 값으로 내가 계산한 값 (제조사 값 아님).
- **[미확인]** = 이번 조사에서 근거를 못 찾음.
- Reddit/X 커뮤니티: 크롤러 차단 이력이 있어 이번에는 조사하지 못함 [미확인]. 대신 Random Nerd Tutorials, Adafruit/Arduino 포럼, GitHub 이슈 등 검색요약만 [2차]로 사용.
- 검색 횟수: WebSearch 약 20회 + 원문 열람(WebFetch/curl) 약 20회. 검색은 25회 이내였고, 열람까지 합치면 초과. 소요 약 15분.

| 방수 프로브 신뢰성 | 데이터시트는 칩 기준. 프로브 케이블/실링(에폭시·수축튜브) 수명과 장기 습열·부패가스 내구성은 제조사별 상이 [미확인]. 위조/저가 칩 이슈 [미확인] |

(2) 0.1초 Fail-Safe를 온도 읽기로 구현하는 것은 변환시간만으로도 사실상 불가(9-bit 93.75 ms는 이미 0.1초 근처). (3) 프로브 열 시정수(초~수십 초)는 미확인이나 핵심온도 응답이 0.1초 단위일 수 없음 |

MQ 예열 결론:
- 제조사 문서는 **48시간 이상**을 요구. 커뮤니티의 "24시간"은 제조사 기준이 아님.
- 신품 또는 장기 보관 모듈은 최대 168시간 에이징 권고.
- 시제품 발표 전 시간 확보 없이 켜자마자 ppm 판독은 근거 없음.
- 매뉴얼은 Rs/R0 상대 판독 구조. 절대 ppm 보증 없음.
- 일반 MQ 계열의 선택성 부족·온습도·노화 민감성은 2차 자료도 동일 [2차] (요약 검색 결과, 원문 미열람).

### '혐기성 부패 = VOC 급증' 성립 여부 (MQ-138)

- 음식물 혐기 부패의 대표 악취: NH3, H2S, 메틸머캅탄, 디메틸설파이드/디설파이드 등 [2차]. 검색요약 출처 https://www.tandfonline.com/doi/full/10.1080/10962247.2013.807318 (직접 접근 403). 보조: https://www.sciencedirect.com/science/article/abs/pii/S0959652624009715
- MQ-138의 대상은 톨루엔·아세톤·알코올·수소. **H2S·머캅탄·NH3는 대상 아님.** 에탄올·아세톤 같은 발효 부산물에는 반응하겠지만 "혐기 vs 호기" 구분 능력 근거는 없음. 세척제·알코올·조리 증기에도 교차반응.
- 따라서 "MQ-138 VOC 급증 = 혐기성 부패"는 **직접 근거 없음.** 표현을 "휘발성 유기증기 상대지표(비특이적)" 수준으로 낮추는 것이 안전.
- 더 논리적인 조합: NH3는 MQ-137(또는 전기화학 NH3), 황화물은 MQ-136(또는 전기화학 H2S). 단, MQ-137/136도 교차감도 정량 자료가 없음.

### 5V AO -> 3.3V ADC 직결 위험

- ESP32-S3 입력 High 최대 VDD+0.3 V (3.3 V 기준 3.6 V), 절대 최대 입력 전압 0.3~3.6 V [직접] ESP32-S3 Datasheet v2.2 Table 5-1, 5-4 https://www.espressif.com/sites/default/files/documentation/esp32-s3_datasheet_en.pdf
- MQ 모듈 AO는 Vc(5 V) 근처까지 상승 가능 [해석]. 직결 시 ESD 다이오드 통전 -> 핀·ADC 손상 위험. 분압(예: 상단 10k/하단 12k, 최대 약 2.7 V) + 100 nF 필터 권장 [계산].
- ADC 11 dB 감쇠의 유효 범위가 0~2.9 V이므로 (아래 5절) 분압비는 이 값 이하로.
- 히터 5 V 2개(MQ-137+MQ-138) 합계 최대 약 1.85 W, 370 mA [계산: 950+900 mW]. 아래 8절 비교 참고.

### 발표 수치 대조

| 발표 수치 | 판정 |
|---|---|
| 180 -> 35 mA | 35 mA는 공식 Modem-sleep 평균(38~40 mA, DFS 없음)과 근접. **180 mA에 해당하는 공식 평균값은 없음**(RX 88 mA, TX 피크 283~340 mA). 180은 개발보드+주변장치 합 또는 ps 끈 실측일 수 있으나 근거 미확인. ESP-IDF는 **기본이 이미 WIFI_PS_MIN_MODEM** [직접]이라 "modem sleep을 켜서 개선"이라는 서술은 기본값 대비로는 성립하지 않을 수 있음(Arduino 기본값 미확인) |
| (75%) 절감 | (180-35)/180 = **80.6 %** [계산]. 35/180 = 19.4 %. 75 %는 산수 불일치. 75 %가 맞으려면 140 -> 35 mA |
| 100~240 -> 15~30 mA | 15~30 mA는 Modem-sleep(+DFS) 19.5~20.7, 저전력 CPU 상태 13~28 mA 대역과 부합. 100~240 mA "전"은 Wi-Fi 상시 활성 TX 피크 340/RX 88 사이이므로 조건 명시 필요. 절감률: 100->15 = 85 %, 240->30 = 87.5 % [계산] |
| 1 Hz MQTT 전송 시 | 초당 TX 버스트(수십 ms, 200~340 mA급) 때문에 평균은 idle modem-sleep 값보다 높음 [해석, 실측 필요] |

### DTIM과 MQTT 제어 명령 지연

- Modem-sleep은 비콘/DTIM 주기로 깨어나 수신 [2차, WebFetch 요약]. MIN_MODEM은 AP의 DTIM 주기를 따름, MAX_MODEM은 더 긴 listen interval 사용, 대가로 지연 증가 [2차]. "DTIM 10이면 대략 1초 지연" [2차, 비콘 100 TU 가정].
- 즉 서버 -> 노드 명령(MQTT 구독 수신)은 DTIM 주기만큼 큐잉될 수 있음. 히터 OFF 명령이 0.1초 안에 도달한다는 보장은 없음 [해석]. 0.1초 Fail-Safe는 **원격 명령 경로로 구현 불가**, 노드 내부 로컬 하드웨어/펌웨어 인터록(과열 임계 시 즉시 릴레이 OFF, 워치독, 통신 두절 시 OFF)로만 성립.
- 노드가 1 Hz로 MQTT publish(송신)하는 것은 지연이 문제되지 않으나, 수신 명령은 지연됨.

### 절감이 히터 대비 몇 %인가

가정: ESP32 0.5 W(발표 기준) 중 modem-sleep 절감분 = (180-35) mA x 3.3 V = 0.48 W [계산]. 

| 히터 전력 | 절감분 0.48 W / 히터 |
|---|---|
| 50 W | 0.96 % |
| 100 W | 0.48 % |
| 300 W | 0.16 % |
| 500 W | 0.10 % |

- 참고: MQ-137 + MQ-138 히터만 최대 약 1.85 W(950+900 mW)로 modem-sleep 절감(0.48 W)의 약 3.9배 [계산]. 릴레이 코일 0.36 W, 미터링·센서 별도. 노드 전체 소비전력 대비로도 Wi-Fi 절감의 비중은 작고, 전체 전력 최적화는 MQ 히터 듀티(예: 간헐 가열)가 훨씬 큼 [해석]. 단, MQ는 예열 48 h 요구와 상충하므로 듀티 사이클링 시 안정성 재검증 필요.
- 결론: "75 % 절감"은 ESP32 칩 단독 기준이고 처리기 시스템 전력으로는 1 % 미만. 발표에서 "배터리/저전력"이 아닌 "AC 전원 처리기"라면 이 절감을 강점으로 내세우기 어려움.
