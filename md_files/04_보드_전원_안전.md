## 0. 핵심 결론 (먼저 읽기)

1. **Pi는 안전 제어에 필요 없다. ESP32 단독 온디바이스 제어로 충분하다.** 근거: (a) 이미 `CoreTempModel.h`(12 tree, 노드 약 17개/트리)와 `CoreTempRegressionEngine.cpp`가 ESP32 펌웨어 폴더에 있다 [코드]. (b) 13특징 RF 추론은 1Hz 데이터에서 10초마다 한 번 돌리는 수준이라 ESP32-S3에 부담이 없다 [코드: SLIDING_INFERENCE_STRIDE=10]. (c) ESP32는 이미 Pi 명령을 믿지 않고 자체 재검증한다 [코드]. Pi는 "대시보드/로그/설정값 제공자"로 격하시키고, 끊겨도 제어 판정은 ESP32가 계속하게 만드는 것을 권고한다.
2. **현재 구조의 실제 위험은 "네트워크 끊김 때 위험해짐"이 아니라 "네트워크 끊김 때 기능이 죽음 + MCU 자체가 멈출 때 릴레이가 켜진 채 남을 수 있음"이다.** 코드는 fail-safe 방향(끊기면 OFF)으로 잘 되어 있다. 대신 (i) 하드웨어 워치독이 없고(`esp_task_wdt` grep 0건) (ii) 독립 하드웨어 과온 차단이 없다. 이 둘이 안전 측면의 진짜 구멍이다.
3. **히터는 AC 220V 직결보다 12V DC 실리콘 히터 패드(수십 W) + 열퓨즈/바이메탈이 20시간 제작·전시장 반입 모두에 유리하다.** 전시장은 전열기구를 제한하고 사전 허가·안전 스위치를 요구하는 사례가 있다(KES 사례 [2차], GIST 규정은 미확인).
4. **RF 예측(60초 창 -> 120초 뒤)은 지금 학습 조건에서는 "제어에 기여한다"고 주장하기 어렵다.** 학습 데이터가 실온 7시간·245샘플이고 예측값을 22~31°C로 clip한다 [코드]. 히터를 켜는 실제 구간(목표 37°C)은 학습 분포 밖이라 RF는 외삽하지 못한다(트리는 학습 때 본 leaf 값만 낸다 — 코드 주석 자체가 이 점을 언급 [코드]). 발표에서는 "예측 기반 조기 OFF"를 데모 가능한 실온 시나리오(목표 25.5°C)로 한정하거나, 지속(persistence)/선형 외삽 기준선과의 비교를 같이 제시해야 방어된다.
5. **시연은 전용 공유기(2.4GHz 고정 채널, 오프라인 LAN) + ESP32 단독 제어 + 사전 녹화 영상 + 예비 보드**로 이중화한다. 프로젝트 코드 주석에 phone hotspot·modem-sleep에서 MQTT stale이 재현됐다고 이미 적혀 있다 [코드].

### 1-3. "Pi가 필요한가?" 결론
- 필요하지 않다. 온디바이스로 옮기는 데 남은 작업은 (1) 추론 결과를 ESP32 내부에서 바로 `determineSafeHeaterOn()`에 연결하고 (2) 히스테리시스+예측 조기 OFF 규칙을 C++로 옮기는 것뿐이다. 판정 규칙은 임계값 비교 몇 개라서 소스 몇십 줄 수준이다 [가정].
- Pi를 남기는 정당한 이유는 "대시보드/로그/시각화/발표용 백엔드"뿐이다. 이 경우 Pi가 죽어도 ESP32는 자체 판정으로 계속 동작(또는 안전 OFF 유지)하도록 역할을 분리한다.
- 대안: 대시보드는 팀원 노트북에서 mosquitto+Node를 돌려도 된다(Pi의 SD 카드·전원·언더볼트 리스크 제거). 이 경우 Pi 섹션(2장)의 리스크가 통째로 사라진다.

### 1-4. 안전 제어를 네트워크 너머에 두는 구조의 위험 (현 구조 적대적 분석)

| # | 위험 | 현 코드 상태 [코드] | 평가 |
|---|---|---|---|
| a | Wi-Fi 끊김/AP 재시작 | `!mqttClient.connected() \|\| mqttRecoveryInProgress` -> OFF | fail-safe 방향 맞음. 대신 데모 중 히터가 꺼져 기능이 죽음 |
| b | 명령 stale | COMMAND_STALE_SEC=20, 추론 주기 10초 | 1개 손실은 견디나 연속 2개(QoS0에서 흔함) 손실이면 OFF. 히터 ON/OFF가 요동칠 수 있음 |
| c | 메시지 지연(신선도 오판) | `lastInferenceRxMs`로 수신 시각만 봄 | 메시지 내용의 생성 시각이 아니라 수신 시각이라, 브로커에 쌓였다가 몰려오는 옛 명령을 신선하다고 오판할 수 있음(확인 필요) |
| d | Pi 서비스 크래시 | 20초 stale로 OFF | 안전 OK |
| e | ESP32 자체 hang(무한루프/WDT 없음) | `esp_task_wdt` 0건 | **위험**: 릴레이가 마지막 상태를 유지하면 가열 지속 |
| f | 센서 탈락/오독 | `core_temperature_valid`, NaN 검사 | DS18B20의 전원 인가 직후 기본값 85°C, 오류값 -127°C 처리 여부는 코드에서 확인하지 못함(데이터시트 미열람이라 [가정]) |
| g | 릴레이 접점 융착 | 감지 수단 없음. INA219 운영 코드 미통합 [코드] | **위험**: SW OFF여도 히터 켜진 채 |
| h | 연속 가열 제한 | MAX_CONTINUOUS_HEATING_SEC=300 | 좋은 방어. 다만 5분 OFF 후 재기동이 또 5분이면 무한 반복되므로 "누적 에너지 한도"가 더 안전 |

원칙: **네트워크 쪽은 "가용성"의 문제이고, 안전은 로컬 하드웨어에서 닫혀야 한다.** SW 판정은 정상 동작 시의 제어, HW 차단은 SW가 틀렸을 때의 보험이다(4장).

권고(Pi를 남기는 경우, 근거가 [가정]인 부분 포함):
1. 공식 PSU 사용, ESP32 5V 레일과 절대 공유하지 않는다(MQ 히터 350mA가 언더볼트를 유발).
2. overlayfs 활성화(시연 전날 최종 이미지 고정) + mosquitto persistence/journald 로그를 tmpfs 또는 최소화. 시연 종료 후 셧다운 절차를 지킨다.
3. systemd watchdog 켜기(`RuntimeWatchdogSec=10`).
4. 부팅 시 3개 서비스가 자동 기동하도록 systemd unit 작성. 20시간 제작 중 가장 자주 잊히는 부분.
5. 예비 SD카드(복제본)를 부스에 둔다.
6. **Pi가 죽어도 ESP32가 안전하게 계속/정지하도록 이미 코드가 되어 있으므로, Pi는 "죽어도 되는 부품"으로 격하**하는 것이 가장 강력한 신뢰성 대책이다.

### 3-3. 브라운아웃·노이즈·접지·디커플링
- ESP32는 Wi-Fi 송신 순간 피크가 크다. 어댑터 용량 부족·긴 배선 전압강하가 브라운아웃 리셋의 주된 원인이다. 벌크 캐패시터를 5V 입력 근처에 두고(예: 470~1000uF, [가정]), 0.1uF를 각 모듈 전원 핀 옆에 둔다. Espressif 하드웨어 가이드는 전원 핀 근처 0.1uF 디커플링을 권고한다 [2차] https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/esp-hardware-design-guidelines-en-master-esp32s3.pdf
- ESP32-S3 datasheet에서 브라운아웃 임계값 수치는 텍스트 검색으로 찾지 못했다(미확인).
- **MQ 센서 아날로그 출력**: 5V 모듈의 AO가 3.3V ADC 핀에 그대로 들어가면 VIH max(VDD+0.3V)와 절대최대(입력 전원핀 3.6V)를 위반할 수 있다 [직접]. 분압(예: 10k/20k [가정]) 또는 모듈 AO 출력 범위 실측 필요. 코드 인수인계 문서는 "5V VCC, median-of-21"만 언급하고 분압 여부는 확인되지 않았다 [코드].
- **ADC 노이즈**: 릴레이 코일·모터·히터 스위칭이 5V 레일에 리플을 만든다. 릴레이 코일 전원을 ESP32 전원과 분리하거나 각각 벌크 캐패시터 추가. 모터는 별도 레일 + 플라이백 다이오드 + 0.1uF 세라믹 [일반 설계 원칙, 미인용].
- **공통 접지**: 모든 레일의 GND를 한 점(스타)으로 묶되, 히터/모터 대전류 복귀선은 센서 GND와 분리한 굵은 별도 경로로 한 점에서 합류. MQ 히터 전류(약 360mA)가 ADC 기준선에 IR 강하를 만들지 않도록 MQ GND 복귀를 ADC 기준에 가깝게 [일반 설계 원칙, 미인용].
- MQ 예열: 제품 문서상 예열 시간이 필요 [MQ-135 검색 스니펫 30초~수 분, 2차]. 시연 시작 최소 수 분 전에 전원 인가.
- 프로젝트 이력: 이전 보드 GPIO5/6 핀 자체가 손상된 사례가 있었다 [코드]. **예비 XIAO 보드 2개 이상 지참**.

## 5. 미생물 처리기 공학 근거

### 5-1. 열 시상수 대비 60초 창·120초 예측의 의미
아래는 **모두 [가정]** 값을 두고 한 자릿수 크기 추정이다. 실제 챔버로 실측해야 한다.
- 챔버 내용물 3kg, 비열 3kJ/kgK, 용기 1kg x 0.5kJ/kgK -> 열용량 C 약 10kJ/K.
- 히터 50W면 승온 속도 = 50/10,000 = 0.005K/s = **0.3K/분**. 10K 올리려면 약 33분.
- 열손실 계수 1~2W/K를 가정하면 시상수 tau = C/G = 약 1.5~3시간.
- 결론: 순수 열용량 관점에서 120초 뒤 온도는 현재 온도에서 최대 약 0.6K 벗어날 뿐이다. **"120초 예측"이 의미 있게 작동하는 유일한 물리는 히터 표면과 온도센서 사이의 열 전달 지연(overshoot 보정)**이다. 이 지연은 배치에 따라 수십 초~분 단위일 수 있다 [가정]. 60초 창은 그 지연을 보기엔 너무 짧지 않지만, 센서 분해능이 문제다.
- 센서 분해능 문제: 프로젝트는 DS18B20을 9-bit로 사용한다 [코드]. DS18B20 9-bit 분해능은 0.5°C 단계다(데이터시트 미열람, 일반 지식 [가정]). 60초 창에서 기울기를 0.3K/분으로 추정하려면 0.5°C 단계보다 작은 신호를 다뤄야 해서, 기울기 특징이 양자화 잡음에 묻힌다. 12-bit(0.0625°C, 변환 750ms [가정])로 올리는 것이 1Hz 샘플링과도 맞다.
- 학습 데이터 한계 [코드]: 원본 1947행/422분, 유효 샘플 245(train 196/val 49), RF val MAE 0.032°C, 예측 clip 22~31°C, 데모 목표 25.5°C, 안전 28.5°C. 실온 유지 상태의 데이터라 target 변화가 거의 없다. MAE 0.032°C는 (i) 시계열 인접 샘플이 훈련/검증에 섞였을 가능성, (ii) 정지 상태에서는 "현재 온도 = 미래 온도"가 거의 정답이라는 점 때문에 **낙관적일 가능성이 높다**. 방어하려면 (1) 시간 순서로 분할한 검증, (2) 지속 예측(T(t+120)=T(t)) 및 선형 외삽 기준선과의 MAE 비교를 제시해야 한다.
- Python 판정 서비스의 목표 37°C, 최대 안전 42°C [코드]는 데모 학습 범위(22~31°C)와 다르다. RF 예측은 학습 때 본 값 범위 안에서만 나오므로 37°C 근처 조기 OFF 규칙은 사실상 작동하지 않는다(트리 leaf 값이 그 범위로 제한).

### 5-2. 미생물 운전 온도 범위
- 퇴비화 문헌: 열발생(thermogenic) 단계 50~80°C에서 고온성 미생물이 관여 [2차] https://link.springer.com/article/10.1186/s40538-023-00381-z (원문 열람은 리다이렉트로 실패, 검색 스니펫만).
- 첨가 균주 예: Bacillus coagulans(고온성) 40~60°C, Bacillus subtilis(중온성) 30~50°C에서 생존 [2차] 특허 https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10017730
- **린클 등 상용 제품의 목표 온도는 공식 문서에서 확인하지 못했다(미확인).** 프로젝트가 잡은 37°C 목표의 근거는 이번 검증에서 확인되지 않았으므로 "가정"으로 명시하거나 사용 균제 제조사 사양을 확인해야 한다.

### 5-4. 교반 모터 전류 감지로 과부하 판단
- 방식: INA219(또는 별도 전류센서)를 모터 전원선에 삽입하고 (1) 정상 교반 전류 기준선을 실측, (2) 기동 돌입 구간(약 0.5~1초)은 무시, (3) 기준선의 1.5~2배를 일정 시간(수 초) 초과하면 정지 후 역회전 시도, 재실패 시 알림 [가정, 일반 설계 원칙, 미인용].
- 현 코드에서 INA219는 운영 코드에 통합되지 않았고 `ina219_valid=false` 하드코딩이다 [코드]. 히터 전류 검증까지 같은 채널이 필요하다면 INA219를 2개(I2C 주소 변경)로 분리하는 것을 고려.
- 모터 노이즈가 5V 로직 레일과 I2C에 유입되므로 모터 전원 분리(3장)가 선행되어야 한다.

### 5-5. 부식성 환경 (암모니아, 습기)
- 암모니아는 구리 및 구리합금에 부식성이며, 침투량·수분량·온도 변화가 심할수록 심하다. 대책으로 컨포멀 코팅, 금/주석 도금 커넥터 [2차] https://www.eng-tips.com/threads/amonia-gas-corrosion-on-electronics.260029/ , https://resources.altium.com/p/circuit-design-tips-pcb-moisture-protection-humid-environments
- 센서 자체: MQ-137 datasheet는 물 튐과 고농도 부식성 가스에서 감도 저하를 경고 [직접] https://cdn.sparkfun.com/assets/b/6/7/5/8/MQ137_datasheet.pdf
- 설계 권고: 전자부는 챔버 밖 격벽 뒤에 두고 센서 프로브만 챔버 내 통기 구멍에 위치. 컨포멀 코팅 시 MQ 센서 개구부는 마스킹. 실리콘 계열 코팅/실란트는 MQ 센서에 금지 [직접, 위 datasheet 1.1]. 릴레이 접점은 밀폐형 사용 권고 [가정].
- DHT11은 상대습도 최대 95% 근처 응결 환경에 취약할 것으로 예상되나 이번에 datasheet를 열람하지 않아 미확인.

## 6. 시연 신뢰성

1. **스마트폰 핫스팟 -> 전용 공유기**: 핫스팟은 유휴 타이머, 재연결 실패("UNSPECIFIED"), 앱 절전 등 문제 사례가 다수 보고됨 [2차] https://www.esp32.com/viewtopic.php?t=8769 , https://github.com/espressif/arduino-esp32/issues/2110 . 프로젝트 코드에도 stale 재현 이력이 있다 [코드].
   - 전용 공유기: 2.4GHz 고정 채널(1/6/11 중 주변 AP가 가장 적은 채널) [가정], SSID 숨김/암호 고정, 인터넷 불필요(오프라인 LAN), DHCP 예약 또는 고정 IP. ESP32-S3는 2.4GHz 전용이므로 5GHz 전용 SSID는 사용 불가 [직접: 데이터시트 제목 "2.4 GHz Wi-Fi + Bluetooth LE"].
   - 현장(대회장)의 2.4GHz 혼잡은 [가정]. 공유기를 부스 안에 두고 안테나가 가까운 거리에 있게 한다.
2. **MQTT QoS/재연결**:
   - PubSubClient는 QoS 0 발행만 가능, 구독은 QoS 0/1, 기본 최대 메시지 256B, keepalive 기본 15초 [직접] https://raw.githubusercontent.com/knolleary/pubsubclient/master/README.md . 따라서 "QoS1로 안전 명령 전달"은 이 라이브러리에서는 불가. 명령 손실은 20초 stale 규칙으로 흡수해야 한다.
   - LWT: 브로커가 keepalive 내 통신 실패·비정상 종료 시 미리 등록된 메시지를 발행. LWT QoS는 일반 메시지와 독립 [직접] https://www.hivemq.com/blog/mqtt-essentials-part-9-last-will-and-testament/ . ESP32 노드 상태를 LWT로 표시하면 대시보드가 "노드 오프라인"을 즉시 표시할 수 있다.
   - 권고: 추론 주기(10초)와 stale 한도(20초)의 비율을 완화(예: 5초 발행/20초 stale) + retained 메시지 + 메시지에 생성 시각/시퀀스 번호를 넣어 오래된 명령 배제 [가정].
3. **발표 중 실패 대비**:
   - ESP32 단독 제어 모드 스위치(Pi/Wi-Fi 없이도 시연 가능): `USE_MOCK_SENSOR_PROVIDER` 같은 시뮬레이션 경로가 이미 존재 [코드].
   - 사전 녹화 영상(핵심 동작 60~90초), 예비 XIAO 보드 2개, 예비 어댑터/케이블, 대시보드 스크린샷 백업, 로컬 CSV 로그(ESP32 시리얼 또는 노트북).
   - 시연 순서: 부팅 -> 센서 예열(수 분 전 미리) -> 정상 -> 고온 주입(과온 차단 시연: 안전 규칙 발동 화면) -> 통신 끊기 시연(Wi-Fi 차단해서 히터 OFF 유지 확인 = "fail-safe" 자랑 포인트).
   - 큰 시연 실패 요인 3개: Wi-Fi, 전원(어댑터/케이블), 센서 예열. 이 3개를 체크리스트로 관리.
